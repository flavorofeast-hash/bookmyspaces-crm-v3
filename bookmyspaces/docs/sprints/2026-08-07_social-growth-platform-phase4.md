# Social Growth Platform, Phase 4 — 2026-08-07

## Scope

Requested: complete a four-sprint "Social Growth Platform" (Social Publishing, AI Content Studio, Social CRM, Marketing Intelligence) whose objective is enquiries → bookings → attributed revenue, not social posting for its own sake. Standing rule for this session: read the whole codebase first, reuse existing architecture, no duplicate tables/APIs, additive migrations only.

## What was found (investigation before any code)

A full read of `src/lib/social/**`, `src/app/api/social/**`, `src/app/api/cron/social-publish`, `src/app/(crm)/{social,content-studio,dashboard/marketing}/page.tsx`, `src/app/api/dashboard/marketing/route.ts`, and migrations 014/030–038 found the large majority of all four sprints already shipped under earlier phase names — `docs/growth/10_SOCIAL_MEDIA.md`'s "list+create only, no publish/AI/cron" note and `docs/growth/04_GAP_ANALYSIS.md`'s "fragile-but-present" framing both predate migrations 036–038 and are now stale (corrected in those files, see below). Concretely already live before this sprint: OAuth-token *storage* (not exchange) + multi-account support (migration 014), a real publish pipeline with adapter dispatch and a monthly calendar (migrations 014/036), AI caption/hashtag/image-prompt generation (`content-generator.ts`), a reference-based media library (migration 032), a Unified Social Inbox with keyword sentiment and manual reply (migration 014), Meta DM capture/AI-response reusing the same `chatWithAI()`/escalation pipeline as WhatsApp, and a Marketing Intelligence dashboard already covering channel/campaign performance, revenue attribution, funnel, campaign ROI, multi-touch attribution, and social/WhatsApp engagement totals (`revenue-intelligence.ts`, `growth-intelligence.ts`, `marketing-ai.ts`, migration 030).

Real, confirmed gaps (verified by reading the code, not assumed): no title/CTA/emoji/short/long content variants or occasion templates (Wedding/Birthday/Corporate/Rooftop/Restaurant/Weekend Stay/Festivals/Offers) in the AI generator; no enquiry/complaint/booking-intent/spam classification or suggested-reply action on Social Inbox interactions; `social_interactions.customer_id` was schema-only, never populated by any code path; publish failures had no automatic retry/backoff/max-attempt cutoff (only an unbounded manual retry); calendar was month-only; no post-level "top content" leaderboard or best-posting-time recommendation. Real OAuth authorization-code exchange/refresh flows, actual image generation, inbound ad-spend tracking, and WhatsApp-click/call-click event capture do not exist anywhere in this codebase and are external-credential/business-integration dependencies, not something closable by writing more application code — disclosed as remaining limitations below, not faked.

## What shipped

- **`src/lib/social/content-generator.ts`** — `generateSocialPostDraft()` extended additively with `options.variant` (`short`/`long`/`emoji`, default `standard`) and `options.template` (`wedding`/`birthday`/`corporate`/`rooftop`/`restaurant`/`weekend_stay`/`festival`/`offer`), plus `title`/`cta` fields on the returned `SocialPostDraft` — same prompt/JSON-parse pipeline, one more guidance line appended, not a second generator. New `generateInteractionReplySuggestion()` for Social Inbox replies (Sprint 3), reusing this file's existing direct-Anthropic-client pattern rather than `operator-assistant.ts` (which needs a full per-customer `AIContext` a public commenter usually doesn't have yet).
- **`src/app/api/social/generate/route.ts`** — accepts/validates the new `variant`/`template` params, unchanged otherwise.
- **`src/lib/social/interaction-service.ts`** — `classifyInteractionIntent()` (enquiry/complaint/booking_intent/spam), reusing `extractLeadDetails()`'s already-built buying-signal extraction rather than a second regex table. `ingestInteraction()` now stores `intent` and, for anything except spam, calls new `linkInteractionToLead()`: phone/email found in the comment → `captureLeadWithJourney()` (existing dedup); no contact info but the same author (platform + `author_external_id`) already has a linked lead from an earlier interaction → reuse that lead, log `lead_re_engaged`; otherwise, only for `enquiry`/`booking_intent`, create one contact-less lead so the *next* interaction from that author finds it via the reuse path. Never sends a welcome message (`sendWelcome: false`) — a public comment isn't an opt-in DM.

- **`src/app/(crm)/content-studio/page.tsx`** — Calendar gained weekly/daily views alongside the existing monthly grid (granularity toggle, same `posts` data, no new fetch); AI generator panel gained variant/template selectors and displays the suggested title/CTA.

## Remaining / follow-up

- Real OAuth authorization-code exchange + refresh-token rotation for any platform (Facebook/Instagram/LinkedIn/X/Google Business) — genuinely does not exist; requires registering real apps with each platform and redirect-URI infrastructure, not just more application code. Today's account connection remains "operator pastes a long-lived token."
- Automated connection health monitoring (auto-transitioning `social_accounts.status` to `token_expired`/`error`) was not built this sprint — still only changes on manual PATCH or an actual publish/reply/webhook call surfacing an error.
- Actual AI image generation (not just prompt drafting) — no image-gen provider is wired into this codebase.
- Inbound ad-spend tracking and WhatsApp-click/phone-call-click event capture — no event source exists anywhere for either; `dashboard/marketing`'s `roiNote` continues to disclose this rather than fabricate a number.
- Approval workflow for social posts is a soft gate (`approved` status exists, but `publish` also works directly from `draft`) — making approval a hard prerequisite before publish was judged out of scope for this pass to avoid changing existing operator workflow without a dedicated design/rollout discussion.
- Sprint 3's spam/complaint/enquiry classification and Sprint 4's engagement score/best-posting-time are keyword-based/deterministic by design (same "cheap now, model-scored later behind the same column" convention `classifySentiment()` already established) — upgrading either to a live model call is a natural, clearly-scoped next step, not started here.

# Revenue Automation & AI Sales Platform, Phase 3 — 2026-08-07

## Scope

Requested: AI WhatsApp Sales Assistant, AI Follow-up Assistant, Marketing Automation (visual builder + specific triggers), WhatsApp Drip Campaigns, Customer Journey extension, Marketing Intelligence expansion, Founder Dashboard additions. Standing rule for this session: extend existing modules, never duplicate functionality.

## What was found (investigation before any code)

A read-only survey of `src/lib/ai/operator-assistant.ts`, `src/lib/whatsapp/`, `src/modules/followups/`, `src/modules/automation/`, `src/lib/customers/journey.ts`, `src/lib/analytics/{revenue,growth}-intelligence.ts`, `src/lib/chief-of-staff/`, `src/lib/founder/`, and the `docs/sprints/2026-08-01_*.md` set found the large majority of this mission already shipped, under different sprint names, in the six days prior to this session:

- **AI WhatsApp Sales Assistant** — contextual reply suggestions (`suggested_whatsapp_reply`, wired into `/inbox`), follow-up generation (`recommended_follow_up`), conversation summary (`conversation_summary`), booking probability + lead priority (`EventSalesAdvisorResult.salesCopilot.bookingProbability`, `leads.ai_score`/`lead_temperature`) all already live in `src/lib/ai/operator-assistant.ts` / `AIAssistantPanel.tsx`. The one real gap: `extractLeadDetails()`'s `buying_signals` (regex-detected booking-intent phrases) were computed on every inbound message by `qualifyLeadFromMessage()` but the return value was discarded by all four call sites — buying intent was detected but never surfaced anywhere.
- **AI Follow-up Assistant** — `/api/cron/ai-followup-assistant` already drafts AI-recommended follow-up content daily into `follow_ups` (status `pending`, `created_by='ai_followup_assistant'`) for human review before the drain cron sends it. Gap: no dashboard ever surfaced these drafts, or Overdue follow-ups, for that review step — only a generic Leads-page follow-up list existed.
- **Marketing Automation** — `/api/cron/marketing-automations` already runs Birthday, Anniversary, Win-back, Repeat Booking, Referral Request, and Proposal Expiry (expires_at-based) triggers. No visual Trigger→Condition→Action builder exists (triggers are code-defined, not operator-configurable) — out of scope for this session's effort budget, disclosed below. Two specifically-requested triggers were genuinely missing: "Proposal not opened" and "Proposal viewed but inactive" — but `src/lib/proposal-intelligence.ts`'s `computeProposalUrgency()` already computes exactly this distinction (`next_action: 'follow_up_now' | 'resend_proposal'`), just never wired to an automated send.
- **WhatsApp Drip Campaigns** — `src/lib/whatsapp/drip-service.ts` already has multi-step sequences with per-step delays (migration 037). Missing: pause/resume (schema only allowed `active`/`completed`/`cancelled`), exit conditions (a converted lead kept receiving drip steps), and performance metrics (none surfaced).
- **Customer Journey** — `src/lib/customers/journey.ts` already logs enquiry→...→repeat-booking/VIP stages onto `activity_logs`, read generically by the existing Timeline UI. No gap found worth extending without a concrete new stage requirement.
- **Marketing Intelligence** — `revenue-intelligence.ts` (channel/campaign performance, funnels) and `growth-intelligence.ts` (repeat-customer analysis, revenue opportunities incl. dormant/lost-opportunity framing, AI growth recommendations) already cover this list. No gap found.
- **Founder Dashboard** — `dashboard/chief-of-staff` (Business Health Score, Today's Priorities, Predictive Insights incl. Revenue at Risk, AI Recommendations, Business Risks/Opportunities) and `dashboard/marketing` already cover this list. No gap found worth a new section given the effort budget.

## What shipped

- **`src/lib/whatsapp/auto-qualify.ts`** — `qualifyLeadFromMessage()` now logs a `buying_signal_detected` journey event (via the existing `logJourneyEvent()`) whenever `extractLeadDetails()` finds booking-intent phrases. Reaches every channel (WhatsApp, social DM, manual lead creation) for free since they all call this one function; visible on the existing Customer Timeline with zero new UI, same reuse pattern `journey.ts`'s own header documents.
- **`src/app/api/cron/marketing-automations/route.ts`** — new `runProposalNudge()` trigger: scans open (`sent`/`viewed`) proposals, calls the existing `computeProposalUrgency()`, refreshes `proposals.urgency_score`/`risk_level`/`next_action` on every scan (closing the staleness gap the 2026-08-01 Chief of Staff sprint doc flagged), and sends a WhatsApp nudge (reusing the existing `proposalFollowUp` template) only when the urgency engine calls for `follow_up_now`/`resend_proposal` — deduped per-proposal via the same `activity_logs.metadata.contains` idiom `runProposalExpiry()` already established.
- **`src/lib/whatsapp/drip-service.ts`** + **migration 038** — `pauseEnrollment()`/`resumeEnrollment()` (new `paused` enrollment status, additive CHECK-constraint widen); an exit condition in `advanceDueDripSteps()` that cancels an enrollment (logging `drip_sequence_exited_goal_met`) when the lead already has a revenue-recognized reservation, reusing the same status set `loyalty.ts`'s `REVENUE_RECOGNIZED_STATUSES` established; `listSequences()` now returns per-sequence enrollment-status counts as `metrics` (active/paused/completed/cancelled) — an honest count, not a fabricated engagement rate. `/api/whatsapp/drip-sequences/enroll` `PATCH` extended to accept `pause`/`resume` alongside the existing `cancel`. Drip Sequences page shows the new metrics and a pause/resume/cancel-by-enrollment-ID control, same "operator pastes an ID" pattern the existing enroll-by-lead-ID control already used.
- **`src/app/api/followups/route.ts`** — `GET` (no `lead_id`) now also returns `aiDrafted` (pending `follow_ups` rows with `created_by='ai_followup_assistant'`, joined with lead name/phone). `POST` gained `send_now`/`dismiss` actions operating on a specific `follow_ups` row (the human-approval step for an AI draft), distinct from the existing `single` action which sends a generic template for a lead.
- **`src/app/(crm)/dashboard/followups/page.tsx`** (new) — AI Follow-up Assistant dashboard: AI-Drafted Follow-ups (Approve & Send / Dismiss), Overdue Follow-ups (Mark done), Pending Nurture. Renders `GET /api/followups` as-is, no client-side computation, same split every other dashboard in this codebase uses. Added to `CRMLayout.tsx`'s nav.

## What was verified vs. assumed

Directly verified this session: `npm run lint` and `npm run build` both run clean after every file group (see below). **Not verified:** migration 038's live production apply status (same disclosed-not-hidden posture as migrations 026/027 per `PRODUCTION_VERIFICATION_REPORT.md`) — run it via the standard `db:migrate:v3`-adjacent process before relying on pause/resume in production. The exit-condition query (`reservations.customer_id` → `leads.id`) reuses the join already used throughout `revenue-intelligence.ts`/`loyalty.ts`, not independently re-verified against a live schema this session.

## Issues found

None new in existing shipped code. One real design correction made mid-build: the proposal-nudge trigger was drafted first as a fully separate urgency calculation before the existing `computeProposalUrgency()` was found via `proposal-intelligence.ts`'s own header comment — corrected before writing any duplicate logic.

## Remaining / follow-up

- No visual Trigger→Condition→Action automation builder exists — every automation trigger (this session's and the six pre-existing ones) is code-defined in `marketing-automations/route.ts`, not operator-configurable via a UI. Building a real builder (condition editor, custom trigger authoring, drag-and-drop) is a genuinely new module, not an extension, and was out of scope for this session's effort budget.
- Drip campaign branching is still linear (`step_order` only) — no conditional "if replied, go to step X" branching exists. The new exit condition (auto-cancel on conversion) is the only conditional behavior added.
- Migration 038 needs live verification before pause/resume is relied upon in production, per this project's standing "presumed vs. confirmed" discipline (`MASTER_DATABASE.md`).
- Buying-intent signals are now logged to the Timeline but not yet folded into `lead_temperature`/`urgency_level` scoring or surfaced as a distinct field on any dashboard — a natural next step, not built here to avoid changing `lead-scorer.ts`'s already-reviewed scoring model without a dedicated design pass.
